The Big Picture

Every component in one frame. Click any box to learn exactly what it does and how it talks to the others. Follow the numbered steps to trace a device's journey from factory floor to authenticated network access.

1
Device sends CSR

The device generates a keypair, builds a CSR with its identity, and sends it to the EST server over HTTPS. The private key stays on the device.

2
CA signs the certificate

The EST server passes the validated CSR to the Certificate Authority module. The CA uses its private key (ca-key.pem) to sign a new X.509 certificate.

3
Certificate returned

The signed certificate is wrapped in a PKCS#7 envelope and sent back. The device now holds: its private key, its signed cert, and the CA cert. That's all it needs.

4
Device connects to Wi-Fi

The device associates with the enterprise SSID. The access point sees it's an 802.1X network and starts an EAP conversation instead of granting access immediately.

5
EAP-TLS handshake

The AP relays EAP packets between the device and FreeRADIUS. A full TLS handshake happens: both sides exchange certificates and verify them against the same CA. Mutual authentication.

6
Access granted

FreeRADIUS sends Access-Accept to the AP. The switch port or Wi-Fi is opened. The device is on the network with a verified, cryptographic identity. VLANs and policies apply.

02 · PKI Fundamentals

Public Key Infrastructure

PKI is the trust framework that makes everything work. Instead of passwords, devices prove identity with cryptographic certificates signed by a trusted authority.

Certificate Trust Chain (click a node to inspect)

Root CA Certificate
Self-signed · ca-cert.pem
EST Server Certificate
Signed by Root CA · server.crt
Device Certificate
Signed by Root CA · issued on enrollment

Asymmetric Cryptography

Every entity has a keypair — a private key (secret) and a public key (shared). Data encrypted with the public key can only be decrypted with the private key. Signatures work in reverse: sign with the private key, verify with the public key.

X.509 Certificates

A certificate binds an identity (like "pump-003.factory") to a public key, signed by a CA. It contains: Subject, Issuer, Validity period, Serial number, Public key, and Extensions (key usage, etc.).

Certificate Signing Request (CSR)

A CSR is how a device asks for a certificate. The device generates a keypair, puts the public key + identity info into a CSR, signs it with its private key (proof of possession), and sends it to the CA.

PKCS#7 Envelope

EST returns certificates in a PKCS#7 container. This is a standard wrapper that can hold one or more certificates. Our server uses a degenerate PKCS#7 (certs-only, no signed data).

03 · EST Protocol

RFC 7030 — Enrollment over Secure Transport

EST defines a simple HTTPS-based protocol for certificate lifecycle management. It replaces older, more complex protocols like SCEP with a clean REST-style API.

GET /.well-known/est/cacerts

No authentication required. Returns the CA certificate(s) in PKCS#7 format so clients can build their trust chain.

Device
EST Server
Requestbash
curl -k https://est-server:8445/.well-known/est/cacerts

Response: Base64-encoded PKCS#7 blob containing the CA certificate (~1,348 bytes)

POST /.well-known/est/bootstrap

Basic Auth required. First-time enrollment for new devices. Returns a short-lived 30-day bootstrap certificate.

New Device
EST Server
Requestbash
curl -k -u estuser:estpwd \
  -H "Content-Type: application/pkcs10" \
  --data-binary @device.csr \
  https://est-server:8445/.well-known/est/bootstrap

Response: PKCS#7 certificate valid for 30 days. Device is now tracked as bootstrap_only.

POST /.well-known/est/simpleenroll

Basic Auth or Client Cert required. Full enrollment — issues a 365-day production certificate.

Device
EST Server
Request with client cert (RA auth)bash
curl -k \
  --cert ra-cert.pem --key ra-key.pem \
  -H "Content-Type: application/pkcs10" \
  --data-binary @device.csr \
  https://est-server:8445/.well-known/est/simpleenroll

POST /.well-known/est/simplereenroll

Basic Auth required. Certificate renewal before expiry. Same process, fresh certificate with new validity dates.

Renew certificatebash
curl -k -u estuser:estpwd \
  -H "Content-Type: application/pkcs10" \
  --data-binary @device.csr \
  https://est-server:8445/.well-known/est/simplereenroll

05 · EAP-TLS + FreeRADIUS

From Certificate to Network Access

This is the endgame. The certificate issued by EST enables the device to authenticate to the Wi-Fi or wired network using EAP-TLS — the strongest 802.1X method.

End-to-End Flow: Device Onboarding to Network Access

Device Generates Keypair

The device creates an RSA 2048-bit (or EC P-256) keypair. The private key never leaves the device. It then builds a PKCS#10 CSR containing its identity (e.g., CN=pump-003.factory.local) and signs it with the private key.

EST Enrollment

The device sends the CSR to /.well-known/est/simpleenroll over HTTPS, authenticating with either a shared password (SRP/Basic Auth) or a pre-provisioned RA certificate. The EST server validates the CSR and signs it with the CA private key.

Certificate Issued

The EST server returns the signed certificate in a PKCS#7 envelope. The device now has: its private key, its signed certificate, and the CA certificate (from /cacerts). This trio is all it needs for EAP-TLS.

Wi-Fi Association (802.1X)

The device connects to the enterprise SSID. The access point (AP) or switch challenges the device using 802.1X. The device responds: "I want to use EAP-TLS."

EAP-TLS Handshake

A full TLS handshake happens inside EAP frames:

  • FreeRADIUS sends its server certificate
  • Device verifies it against the CA cert
  • Device sends its EST-issued certificate
  • FreeRADIUS verifies it against the same CA cert
  • Both sides derive session keys — mutual authentication complete

Network Access Granted

FreeRADIUS sends Access-Accept to the AP/switch. The port is opened. The device is on the network with a cryptographically verified identity. VLAN assignment, ACLs, and policies can be applied based on certificate attributes.

FreeRADIUS Configuration (Key Parts)

eap.conf — EAP-TLS Module

conf
eap {
  default_eap_type = tls

  tls-config tls-common {
    # FreeRADIUS server certificate
    certificate_file = /etc/raddb/certs/server.pem
    private_key_file = /etc/raddb/certs/server.key

    # Same CA that EST uses to sign device certs
    ca_file = /etc/raddb/certs/ca-cert.pem
  }
}

The Shared Trust Anchor

The critical link between EST and FreeRADIUS is the CA certificate. Both systems trust the same CA:

  • EST server uses ca-key.pem to sign device certificates
  • FreeRADIUS uses ca-cert.pem to verify those same certificates
  • No direct integration needed — they share a trust anchor
This is the beauty of PKI — systems that have never communicated can trust each other through a shared CA.

07 · Authentication

Dual Authentication System

Two independent methods, tried in order: RA Certificate first, then SRP Basic Auth as fallback.

How SRP Works

SRP (Secure Remote Password, RFC 2945) never transmits the password. Instead, the server stores a salt and verifier derived from the password. In our implementation, we use it through HTTP Basic Auth over TLS:

  1. Client sends Authorization: Basic base64(user:pass)
  2. Server extracts credentials from the header
  3. Server hashes password with PBKDF2-HMAC-SHA256 (100,000 iterations)
  4. Compares against stored verifier
  5. Match = authenticated, mismatch = 401

User Management CLI

bash
# Add a new user
python-est user add factory_gateway -p s3cureP@ss

# List all users
python-est user list

# Remove a user
python-est user remove old_device

# Default user (auto-created on startup):
# Username: estuser  Password: estpwd
# Override via EST_DEFAULT_USER / EST_DEFAULT_PASS env vars

RA Certificate Authentication

For automated enrollment (manufacturing lines, gateways), a Registration Authority certificate is used. This is a client certificate pre-provisioned on the gateway.

  1. Gateway presents client certificate in TLS handshake
  2. Nginx validates cert against CA and extracts fields
  3. Nginx forwards headers to EST server:
    • X-SSL-Client-Verify: SUCCESS
    • X-SSL-Client-S-DN: CN=gateway-01
    • X-SSL-Client-Serial: 0A1B2C...
    • X-SSL-Client-Fingerprint: SHA256:...
  4. EST server checks X-SSL-Client-Verify == SUCCESS
  5. Request proceeds without password

Authentication Precedence

if X-SSL-Client-Verify == "SUCCESS"
  ✓ RA cert auth — proceed
elif Authorization header present
  ✓ SRP auth — verify password
else
  ✗ 401 Unauthorized

Why two methods? SRP is for interactive/manual enrollment. RA certs are for automated, high-volume provisioning where you can't type a password.

Dashboard crashed when uptime exceeded 24 hours ("64 days, 8:12:34"). Parser only expected H:MM:SS format. Fixed with regex that handles both.

Rich panels with emoji characters crashed on Windows cp1252 console encoding. Removed emoji from CLI output; plain text works universally.

Auth on Fresh Install

ensure_default_user() was only called from the dashboard endpoint. Fresh server returned 401 on /bootstrap. Moved to startup + enrollment routes.

11 · Glossary

Key Terms

EST
Enrollment over Secure Transport. RFC 7030 protocol for certificate management over HTTPS.
PKI
Public Key Infrastructure. The system of CAs, certificates, and keys that establishes digital trust.
CA
Certificate Authority. The trusted entity that signs certificates. Holds the root private key.
CSR
Certificate Signing Request (PKCS#10). A device's formal request for a certificate, containing its public key and identity.
PKCS#7
Cryptographic Message Syntax container format. Used by EST to deliver certificates. Also called CMS.
EAP-TLS
Extensible Authentication Protocol — Transport Layer Security. Certificate-based Wi-Fi/802.1X authentication. The strongest EAP method.
802.1X
IEEE standard for port-based network access control. The framework that EAP runs inside of for Wi-Fi/wired auth.
FreeRADIUS
Open-source RADIUS server. Handles 802.1X authentication, validates device certificates during EAP-TLS handshake.
SRP
Secure Remote Password (RFC 2945). Password authentication protocol where the password is never transmitted.
RA
Registration Authority. A trusted intermediary (like a gateway) with its own certificate, authorized to enroll devices on behalf of others.
TLS Termination
Nginx decrypts HTTPS traffic, inspects client certificates, then forwards plain HTTP to the backend. The backend never handles TLS directly.
Mutual TLS (mTLS)
Both client and server present certificates. EAP-TLS is a form of mTLS — the device and RADIUS server both prove identity.
